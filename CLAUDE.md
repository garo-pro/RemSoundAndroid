# CLAUDE.md — RemSoundAndroid

Android companion app (receive + microphone send) for the Windows **RemSound** app (https://github.com/Ednunp/RemSound), ported from the Apple version (https://github.com/jonathans859/RemSoundApple). The C# in the Windows repo is the wire-protocol spec — when in doubt read `src/RemSound.Core/` (`RemPacket.cs`, `RemSoundCrypto.cs`, `PeerDiscoveryService.cs`, `HeartbeatService.cs`) and `src/RemSound.Receiver/`. The Apple port is the design reference for behaviour and UI: it has already paid for the mistakes listed under "Pitfalls" below, and its `CLAUDE.md` carries the long-form reasoning.

## Build workflow

- Validation happens on GitHub Actions (`.github/workflows/ci.yml`: unit tests, lint, debug + unsigned release APK) and locally through Android Studio or `./gradlew`. There is **no Play Store step** anywhere in this repo — no keystore, no signing secret, no upload.
- `./gradlew :remsoundkit:testDebugUnitTest` is the fast gate. Everything that keeps Windows interop working is pinned there.
- **Commit, but never `git push` unless asked** — the user pushes. LF→CRLF warnings on commit are normal; ignore them.
- New shared code goes in `remsoundkit/src/main/java/com/garo/remsound/kit/`. The `app` module is UI, the foreground service, and the entry point only.

## Wire contract — breaking any of these silently breaks Windows interop

- **Header**: 12 bytes LE — magic `RMND`, version **1** (reject all else), type, uint16 streamId (0 coerces to 1), uint32 sequence. One UDP port **47830** for audio + heartbeat; discovery on **47821**.
- **Format payload**: accept 32 / 36 (+lane byte @32) / 44 (+8-byte password fingerprint @36) bytes. Field @28 is `frameSamplesPerChannel` — a **sample count, not milliseconds**. Unknown lane values clamp to `MIXED`, never reject.
- **Crypto**: PBKDF2-HMAC-SHA256, **100 000** iterations, salts `"RemSound.v1.audio-key"` (32-byte key) / `"RemSound.v1.fingerprint"` (8 bytes). AES-256-GCM packet layout is **`nonce(12) ‖ tag(16) ‖ ciphertext`** — the JCE emits `ciphertext ‖ tag`, so the pieces are reordered explicitly in `RemSoundCrypto.kt`. Cross-impl PBKDF2 vectors are pinned in `CryptoTest.kt`; if they fail, interop is broken. The iteration count is a **cross-port** contract: upstream v5.6 raised it to 600 000 for one day and broke every port outright; v5.7 reverted and annotated the constant "MUST stay 100k". Never mirror an iteration-count change without the user confirming every port moves together. PBKDF2 is spelled out over `Mac` rather than taken from `SecretKeyFactory`, because the JCE picks its own password encoding for the `char[]` and that differs between providers — the contract is the UTF-8 bytes. An empty password uses a single zero byte as the HMAC key (the JCE rejects an empty one); HMAC zero-pads short keys, so that derives the identical value the other ports get from a zero-length password. Pinned by the `""` vector. Send-side nonces are **counter-based** like the Windows sender — random 48-bit prefix per key ‖ 48-bit counter (`NonceSequence`, reset on every key rebuild), never a fresh random nonce per packet.
- **PCM**: whole int24-LE frame encrypted, then split into ≤1454-byte parts with a 6-byte sub-header → reassemble **then** decrypt; parts arrive in order, a missing part drops the frame.
- **Opus**: per-packet decrypt → decode; on a single-packet gap decode the next packet with `decodeFec = true` first. Frame-size floor 120 samples.
- **Discovery JSON**: PascalCase keys, matched **case-sensitively** by Windows (`InstanceId`, `Name`, `AudioPort`, `CanSend`, `CanReceive`). 1.5 s announce, 8 s expiry. Unicast is what crosses VPNs; receiving an announcement auto-adds the source IP as a unicast target.
- **Heartbeat**: 1 Hz ping, streamId 0xFFFF, payload = kind byte + int64 LE monotonic ms echoed verbatim in the pong. Pongs match peers **by IP only**. Heartbeats leave the same socket audio arrives on (shared NAT pinhole; also claims our relay slot).
- **Relay address-proof** (type **10**): echo the packet back **verbatim to its source**, from the audio socket, and **ungated by the allow-list** — the challenge comes from the relay, not from a selected peer.
- **Allow-list**: gate audio/format by source **IP**, not port. Sessions keyed (endpoint, streamId); on a new streamId from the same peer, supersede old sessions **only if the lane matches** (BothIndependent senders run two lanes per peer).

## Locked product decisions

- v3.x protocol only; no legacy, no relay-v2 lobby, no recording, no PCM send.
- **The UI mirrors the Apple port control for control**: a title bar with a persistent About button over four tabs — Connectivity (status / connection / peers / add peer), Send & Receive (receive toggle, mic send, password), Audio (playback options), Profiles. The section footers are load-bearing, not decoration: a screen reader reads them as the context for the controls above, and several carry the only explanation of what a switch costs.
- **Screen-reader accessibility is the top priority**: every control labeled, status lines are plain sentences, audio start/stop fires cues plus a spoken announcement. Row operations follow the Apple port's pitfall — a long-press menu is a touch convenience a screen reader cannot reliably reach, so every row operation is ALSO an explicit `CustomAccessibilityAction`.
- **Profiles are local to the device.** No cloud sync. The Apple port's iCloud design works only because iCloud Keychain carries the passwords end-to-end encrypted while the profile JSON stays password-free; without an equivalent, syncing is not worth the exposure. The password-never-in-the-JSON rule still holds and is pinned by a test.
- **`ReceiverProfile.fromJson` decodes every field after `id`/`name` with a default** — keep it that way when adding fields. The read path treats a decode failure as "no profiles", so a stricter decoder meeting older JSON would silently WIPE the user's profiles.
- **Send and receive are independent** (Windows v5 parity): the socket, heartbeats, and discovery run for the service's lifetime; "Receive audio" gates playback ONLY. `AudioOutput` deliberately keeps its track running — stopping it drops the audio-focus claim that keeps the stream alive with the screen off, and would kill an active mic capture.
- Both toggles are persisted. Send saved as on resumes at launch, consumed from `startupSendPending` at the END of the first `start()` — flipping it earlier re-enters `start()` from the setter.
- **Continuous latency auto-tune** (opt-in, default off like upstream's): every 5 s it recommends `secondHighest(arrival gap) + secondHighest(render gap) + 5 ms`, floored at `ceil(1.5 × frameMs)` and capped at 200 ms, raising in one step but lowering at most 5 ms per tick, with 5 ms hysteresis. **Second**-highest, not peak: one transient second must not drive the target. `decide` is pure so CI can test it without audio or network. Gating on underruns REQUIRES the cause split in `SessionPlayout` — `tuneBlockingUnderruns` vs `deviceGulpUnderruns`; upstream found that gating on the undifferentiated total pins the target high forever. Auto-tune moves are runtime state: `autoTuneIsMovingTarget` keeps the setter from persisting over the user's value, and it uses the soft (`drainOnLower = false`) path.
- **Volume boost** (off / +3 / +6 / +12 dB) multiplies into the mixer gain BEFORE the soft limiter, so a boost compresses instead of clipping. Discrete steps, not a wider volume slider — 0–400 % is ~80 screen-reader swipes wide, and one control mixing "volume" with "gain that distorts" hides that the top of the range is not free. Device-local; not in profiles.
- Mic send: Opus-only, one mixed lane, 48 kHz stereo 192 kbps (RESTRICTED_LOWDELAY, complexity 10, VBR, FEC, 10 % loss bias) — mirrors the Windows sender. One endpoint per selected peer.
- Password in `SecureStore` (Android Keystore AES-GCM over SharedPreferences), never in plain preferences. Control packets (type 5) parsed and ignored.
- minSdk 26, targetSdk 35, one application id `com.garo.remsound`.

## Pitfalls (inherited from the Apple port, plus the Android-specific ones)

1. **Never poll audio-input hardware on a timer.** Enumeration is audio-server IPC and causes audible crackling. Refresh inputs only on `AudioDeviceCallback` and at capture start.
2. Multi-homed peers (LAN + Tailscale) announce from several source IPs. Never key row identity, allow-list, or heartbeat tracking on a single address — `PeerAnnouncement.addresses` keeps all paths; selection/allow/track must cover ALL. Pinned by a test.
3. Jitter-buffer click-trim must keep a cushion ABOVE target latency, never trim to bare target (causes sustained underruns on bursty VPN paths) — see `SessionPlayout.write`.
4. Connect/disconnect cues must keep the Windows hysteresis rule (connected = audio within 3 s OR healthy heartbeat; lost = no audio AND heartbeat unreachable ~5 s; in between holds state) — a bare audio-window check fires false disconnect+connect pairs on 2-second Wi-Fi stalls. See `ReceiverController.updateCues`.
5. **Wi-Fi filters broadcast frames with the screen off**, which is exactly the traffic discovery listens for. `RemSoundService` holds a `MulticastLock` for its lifetime; without it LAN peers quietly stop appearing and only manual addresses keep working.
6. **From API 34 the foreground-service type is named at the `startForeground` call, and the system checks the permission behind every type it is given.** Claiming `microphone` while only receiving throws for a user who never granted RECORD_AUDIO, so the type follows whether capture is actually on (`startForegroundCompat`).
7. **A headset's single button sends one key for both directions**, and the default `MediaSession` dispatch picks `onPlay`/`onPause` from the state it believes we published — which is what makes the button one-way (the Apple port hit exactly this: AirPods send `pause` for every stem press, in every state). `RemoteTransportControls.onMediaButtonEvent` therefore decides the direction itself and toggles. Two commands from one physical press are coalesced by a 0.5 s gate in the same place; keep that gate if you touch this.
8. The media buttons need the app to actually hold audio focus. With "Don't mix with other sounds" off the session never takes focus, so no re-publish can reclaim anything — the transport is *released* rather than left registered against a system that will never route a press to us, and the Diagnostics panel says so.
9. Bluetooth mics are a trap for a streaming app: opening a headset's mic drops the link into handsfree mode, so the mic arrives at 16/24 kHz on the Bluetooth clock AND the headset's own output degrades. Symptoms look unrelated to Bluetooth — the *remote* end hears periodic clicks from clock drift while local monitoring is clean. Diagnose by retesting on the built-in mic.
10. Android exposes no kernel delivery timestamp through the datagram API, so inter-arrival gaps are timed on the receive thread and measure our own scheduling as much as the network. The Diagnostics line says "thread-timed" for that reason — do not quietly relabel it.

## Architecture (`remsoundkit/src/main/java/com/garo/remsound/kit/`)

- Wire codec: `RemPacket.kt`, `AudioFormatInfo.kt`. Crypto: `RemSoundCrypto.kt` (`AudioDecryptor` network-thread only; `AudioEncryptor` capture-thread only).
- Network: `UdpSocket.kt` (IPv4 only, one blocking-receive thread), `PeerDiscoveryService.kt`, `HeartbeatService.kt`.
- Receive path: `AudioReceiverEngine.kt` (socket owner, dispatch, sessions, allow-list) → `StreamSession.kt` (decode) → `SessionPlayout.kt` (jitter buffer, fades — fades shape a per-session scratch BEFORE summing, never the shared mix buffer) → `PlayoutMixer.kt` (sum, volume, limiter) → `AudioOutput.kt` (AudioTrack + audio focus). `StreamDiagnostics.kt` is measurement-only telemetry hanging off the same path, aggregate per engine so counts survive streamId rotation and idle pruning.
- Send path: `MicrophoneCapture.kt` (AudioRecord on its own thread, 10 ms reads, mono duplicated to both channels) → `AudioSendEngine.kt` (accumulate → Opus encode → encrypt → targets; format re-announce every 250 ms) via `OpusStreamCodec.kt`.
- App layer: `ReceiverController.kt` (the façade, 1 Hz refresh tick, `StateFlow` state; the UI and the service share ONE instance via `ReceiverController.shared`), `RemoteTransportControls.kt`, `Profiles.kt`, `Settings.kt` (SharedPreferences + `SecureStore`).
- The refresh tick has two halves. The **functional** half (cues, DNS retry, send targets, render-block demand, interruption recovery, packet sampling, auto-tune) runs whether or not a UI is on screen — this app spends most of its life with the screen off. The **presentation** half (status strings) is gated on `setUiVisible`.
- `app/`: `MainActivity` (Compose host, permission prompts, spoken announcements), `RemSoundService` (foreground service, multicast lock, notification), `ui/` (the four tabs, the form building blocks, the rows, the dialogs).
